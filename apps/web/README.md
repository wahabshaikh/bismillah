# @bismillah/web

The web app: [TanStack Start](https://tanstack.com/start) (React 19) on Cloudflare Workers,
built with the [Cloudflare Vite plugin](https://developers.cloudflare.com/workers/vite-plugin/).
Pages are server-rendered by a Worker; JS, CSS and everything in `public/` are served as
[static assets](https://developers.cloudflare.com/workers/static-assets/) straight from the edge.

It talks to the [API Worker](../api) through [`@bismillah/api-client`](../../packages/api-client),
a Hono RPC client typed from the API's routes, and uses [`@bismillah/ui`](../../packages/ui) for
components and design tokens.

## Local development

```sh
pnpm dev    # from the repo root: API on :8787, this app on :3000
```

Vite runs the server render inside `workerd`, the same runtime as production. To try the
production build locally, run `pnpm build && pnpm preview` (also on :3000) with the API running.

The API URL defaults to `http://localhost:8787`. To point at another API, copy `.env.example`
to `.env.local` and set `VITE_API_URL`.

## How it fits together

| Piece                  | Where                            | Notes                                                    |
| ---------------------- | -------------------------------- | -------------------------------------------------------- |
| Routes                 | `src/routes/`                    | File-based; `src/routeTree.gen.ts` is generated by Vite  |
| Router + Query client  | `src/router.tsx`                 | One `QueryClient` per request during SSR                 |
| API client             | `src/lib/api.ts`                 | `api.uploads.$get(...)`, fully typed, sends credentials  |
| Auth client            | `src/lib/auth.ts`                | Better Auth's React client, pointed at the API           |
| Signed-in pages        | `src/routes/_authed.tsx`         | Redirects to `/sign-in`; rendered in the browser (below) |
| Styles                 | `src/styles.css`                 | Tailwind CSS v4 + `@bismillah/ui/theme.css`              |

**Why signed-in pages skip SSR.** The session cookie is set by the API origin, so the web
Worker never sees it and can't render a user's data on the server. The `_authed` layout sets
`ssr: false`, so its pages render in the browser, where requests to the API carry the cookie.
Public pages are fully server-rendered.

**Same site, different origins.** The browser only sends the API's cookie from the web app if
both are on the same site: `localhost:3000` and `localhost:8787` locally, and sibling
subdomains such as `app.example.com` and `api.example.com` in production. Two unrelated
domains (or two `*.workers.dev` subdomains, which are separate sites) won't work.

## Deploying

1. Deploy the API first (see [its README](../api/README.md)) on its own domain, e.g.
   `api.example.com`, and add this app's origin to the API's `TRUSTED_ORIGINS`.
2. Give this Worker a custom domain on the same site, e.g. by adding
   `"routes": [{ "pattern": "app.example.com", "custom_domain": true }]` to `wrangler.jsonc`.
3. Build with the API URL and deploy:

   ```sh
   VITE_API_URL=https://api.example.com pnpm run deploy
   ```

`VITE_API_URL` is inlined into the client bundle at build time, so set it wherever you build
(locally or in CI).

## Staying inside the $5/month plan

- **Static assets are free.** Requests for JS, CSS, images and fonts are served from the edge
  without invoking the Worker, so they don't count against the 10M included requests.
- **One Worker invocation per page load.** Only the HTML render runs the Worker; client-side
  navigation after that hits the API directly.
- **No server-to-API hops.** Data loads from the browser, so the web Worker never spends
  CPU time proxying API calls.
